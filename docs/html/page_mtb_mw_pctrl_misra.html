MISRA-C:2012 Compliance

This section describes MISRA-C:2012 compliance and deviations for the Power Control Service Layer Middleware Library.

MISRA stands for Motor Industry Software Reliability Association. The MISRA specification covers a set of 10 mandatory rules, 110 required rules and 39 advisory rules that apply to firmware design and has been put together by the Automotive Industry to enhance the quality and robustness of the firmware code embedded in automotive devices.

The MISRA specification defines two categories of deviations (see section 5.4 of the MISRA-C:2012 specification):

  • Project Deviations - deviations that are applicable for particular class of circumstances.
  • Specific Deviations - deviations that are applicable for a single instance in a single file.

Project Deviations are documented in current section below.

Specific deviations are documented in the source code, close to the deviation occurrence. For each deviation a special macro identifies the relevant rule or directive number, and reason.

Project Deviations

The following project-wide deviations from MISRA-C:2012 are documented. These deviations are applicable across the Power Control Service Layer Middleware Library and are recorded in the Coverity deviation configuration file.

MISRA Rule Rule Description Description of Deviation(s)
Directive 4.2 All usage of assembly language should be documented. The Power Control Service Layer Middleware Library uses assembly statements to access core registers in several places. These locations start with __ASM or __asm (e.g., LDREX / STREX in mutex.h, CPSID / BKPT in stack_mon.c).
Directive 4.4 Sections of code should not be "commented out". Allow commenting out code sections. Commented-out code is used for documenting alternative configurations and is maintained alongside active code.
Directive 4.8 If a pointer to a structure or union is never dereferenced within a translation unit, then the implementation of the object should be hidden. Deviated since structure typedefs might be included from an external library (e.g., PDL, CMSIS) that is not under the project's control.
Directive 4.9 A function should be used in preference to a function-like macro. Function-like macros are used to allow more efficient code. The library uses macros for shared-memory section placement, atomic operations, and compiler attribute abstraction.
Rule 1.2 Language extensions should not be used. The Power Control Service Layer Middleware Library supports the ISO:C99 standard. Compiler-specific extensions are used for memory section placement (__attribute__((section(...)))), function inlining, and CMSIS intrinsics (__LDREXW, __STREXW).
Rule 2.5 A project should not contain unused macro declarations. The library provides a configurable API. Configuration macros in default configurations may not be used if the user overrides them. This allows for a two-tier configuration architecture.
Rule 3.1 The character sequences
/* and //
shall not be used within a comment. 		Special comment symbols are required for Doxygen documentation support. This does not have any functional impact.
Rule 5.5 Identifiers shall be distinct from macro names. This rule applies to ISO:C90 standard. The Power Control Service Layer Middleware Library conforms to ISO:C99 that does not require this limitation.
Rule 5.8 Identifiers that define objects or functions with external linkage shall be unique. During code analysis, the same source files are compiled multiple times with device-specific options. All object and function identifiers are actually unique for each specific run. Additionally, shared-memory variables and linker-provided symbols (__INITIAL_SP, __STACK_LIMIT) require redeclaration in C, making duplicate external linkage inherent and intentional.
Rule 8.7 Functions and objects should not be defined with external linkage if they are referenced in only one translation unit. The library provides API to the application. Functions and objects with external linkage are part of the public API, which is defined for application-level use only.
Rule 8.13 A pointer should point to a const-qualified type whenever possible. The const qualifier is not enforced on pointer parameters because a single API function signature is shared across multiple variant implementations, where one variant may modify the pointed-to data and another may not.
Rule 11.4 A conversion should not be performed between a pointer to object and an integer type. The cast from unsigned int to pointer does not have any unintended effect, as it is a consequence of the definition of a structure based on hardware registers.
Rule 15.5 A function should have a single point of exit at the end. Early returns are used for parameter validation guard clauses, which improves readability. This rule has been disapplied in MISRA-C:2025.

Specific Deviations

The following specific deviations apply to individual files in the Power Control Service Layer Middleware Library. These findings were identified during Coverity static analysis and are documented here with rationale.

MISRA Rule Rule Description File(s) Description of Deviation(s)
Rule 5.3 An identifier declared in an inner scope shall not hide an identifier declared in an outer scope. mutex.h, cy_ppca_shm_tb.h The parameter name mutex in mutex_lock() and mutex_unlock() shadows the file-scope mutex array declared in cy_ppca_shm.h. Similarly, the struct member and parameter name mutex in the triple-buffer API (cy_ppca_shm_tb_blk_t and Cy_PPCA_SharedMem_TB_Init) shadows the global array. The name is retained for API clarity; the identifiers serve distinct purposes and no ambiguity exists in practice.
Rule 5.8 Identifiers that define objects or functions with external linkage shall be unique. cy_ppca_shm_tb.h, mutex.h, stack_mon.h The mutex identifier is used for both the global shared-memory array and as a structure member / function parameter across translation units. Linker-provided symbols (__INITIAL_SP, __STACK_LIMIT) must be redeclared in C to reference them; the duplicate external linkage is inherent and intentional.
Rule 8.4 A compatible declaration shall be visible when an object or function with external linkage is defined. cy_ppca_shm_common.c, basic_sched.c Shared-memory variables placed in .cy_ppca_shm via CY_SECTION_PPCA_SHM_SUB are defined in the source file with section attributes that differ from the plain extern declaration in the header.
Rule 8.5 An external object or function shall be declared once in one and only one file. basic_sched.c The SystemCoreClock variable is declared locally in addition to the system header. This is required because the scheduler must access the system clock frequency for SysTick configuration without depending on a specific BSP header include order.
Rule 8.15 All declarations of an object with an explicit alignment specification shall specify the same alignment. cy_ppca_shm.h Shared-memory variables have extern declarations in headers without alignment attributes. The definition controls placement, and the declaration provides type-compatible access.
Rule 10.5 The value of an expression should not be cast to an inappropriate essential type. basic_sched.c A uint32_t tick difference is cast to int32_t for wrap-around-safe time comparison in sched_task_is_due() and sched_pick_best_task(). The unsigned subtraction result is stored in an intermediate variable before casting, making the intent explicit. This is a standard idiom for modular tick arithmetic on 32-bit timers.
Rule 10.8 The value of a composite expression shall not be cast to a different essential type category or a wider essential type. stack_mon.c Pointer subtraction result is cast to size_t for stack size calculations. The pointer difference within the linker-defined stack region is always non-negative, making the cast safe and intentional.
Rule 11.3 A conversion shall not be performed between a pointer to object type and a pointer to a different object type. stack_mon.c, stack_mon.h Linker-provided symbols __STACK_LIMIT and __INITIAL_SP are typed as unsigned int by the toolchain but cast to uint32_t* for stack monitoring. On the 32-bit ARM target both types are identical in size and alignment.
Rule 18.1 A pointer resulting from arithmetic on a pointer operand shall address an element of the same array as that pointer operand. stack_mon.c The stack fill loop computes limit + 1 where limit points to the linker-defined __STACK_LIMIT symbol. Coverity treats linker symbols as singletons, but the symbol actually represents the base of a contiguous stack memory region. Pointer arithmetic within this region is safe and intentional.
Rule 18.3 The relational operators shall only be applied to pointers that point into the same object. stack_mon.c The comparison ptr < top compares pointers derived from two different linker symbols (__STACK_LIMIT and __INITIAL_SP). Both symbols bound the same contiguous stack memory region defined in the linker script, so the relational comparison is well-defined on this target.
Rule 20.5 #undef shall not be used. mutex.h #undef is required to replace the CMSIS __CLREX macro with an IAR-compatible form. The CMSIS definition uses an asm expression that IAR does not support in expression context.
Rule 21.1 #define and #undef shall not be used on a reserved identifier or reserved macro name. cy_ppca_shm.h, mutex.h The macros __SM_ATTR__, __SM_ATTR_SUB__, __SM_ATTR_NV__, and __SM_ATTR_SUB_NV__ in cy_ppca_shm.h use double-underscore naming to match the convention of the existing shared-memory infrastructure. These macros are conditionally compiled only when CY_PPCA_SHM_ENABLE_OLD_API_COMPATIBILITY is set to 1, and are retained for backward API compatibility; new code should use CY_SECTION_PPCA_SHM directly. In mutex.h, the CMSIS-defined __CLREX macro is redefined with an IAR-compatible form. These names do not collide with any compiler-defined or standard library reserved identifiers on the supported toolchains.
Rule 21.2 A reserved identifier or reserved macro name shall not be declared. cy_ppca_shm.h The shared-memory section attribute macros (__SM_ATTR__, __SM_ATTR_SUB__, __SM_ATTR_NV__, __SM_ATTR_SUB_NV__) use double-underscore naming which is reserved by the C standard. These macros are conditionally compiled only when CY_PPCA_SHM_ENABLE_OLD_API_COMPATIBILITY is set to 1, and are retained for backward API compatibility; new code should use CY_SECTION_PPCA_SHM directly. They do not conflict with any standard library or compiler-reserved identifiers on the supported toolchains.
ARRAY_VS_SINGLETON Out-of-bounds access (Coverity semantic checker). stack_mon.c Coverity flags pointer arithmetic on linker-provided stack symbols as out-of-bounds access on a singleton object. The linker symbols mark the boundaries of a contiguous stack region, not singleton objects. Declaring them as arrays (extern uint32_t __STACK_LIMIT[], extern uint32_t __INITIAL_SP[]) in stack_mon.h resolves the false positive.
